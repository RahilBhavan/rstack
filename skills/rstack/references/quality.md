# Quality and evaluation

The target is useful results with fewer unsupported claims, avoidable corrections
and unnecessary steps. Catalog size and model review scores are not quality metrics.

For changes to this router:

1. Check catalog discovery, variants, drift, plan resolution and installation through
   the CLI's public interface with synthetic roots.
2. Exercise clean-copy setup without the maintainer's private state.
3. Forward-test meaningful routing changes with a fresh agent when authorized and
   useful. Give original requests and raw inputs, not the intended answer. Retain
   exact artifact/check paths and platform limits. One review repair allowance.
4. Record actual failures and repair the responsible step; do not weaken the cases
   to get a passing result.

For a later comparison with the previous setup, freeze representative real tasks
and original acceptance criteria before running either version. Include direct
questions and small edits as well as builds, research, public figures and workspace
tasks. Compare factual errors, missing constraints, inappropriate skill/tool use,
human corrections, acceptance, elapsed time and observed model cost. Use held-out
tasks and record missing measurements honestly. No recurring evaluation is installed.

A good routing result uses the appropriate surface, reads the owning instructions,
does not start unrelated workflows, preserves authorization and produces evidence
for its completion claim. Scripts test filesystem/planning behavior; they do not
prove every installed skill or measure human usefulness.
